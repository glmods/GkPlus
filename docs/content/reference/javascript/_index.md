Reference for mod authors and developers writing JavaScript against GkPlus. It
describes the `"gk"` QuickJS module a script imports, the `ImGui` interface the
overlay callback receives, and the contracts an entry module exports.

The pages themselves are **generated by TypeDoc from `types/gk.d.ts` and
`types/imgui.d.ts`** and are served at [`/api/js/`](/api/js/). Everything below is
the map into them.

## Building it

```bash
npx -y -p typedoc@0.28 -p typescript@5.9 typedoc --options types/typedoc.json
```

Output lands in `docs/static/api/js/`, which Hugo serves at `/api/js/`. Both
version pins are required: TypeScript and TypeDoc are deliberately not
dependencies of this repository, and a bare `-p typescript` resolves to a major
release TypeDoc refuses as a peer.

The run emits no warnings. A warning from it is always a `{@link}` naming a
member that no longer exists.

Three checks hold the declarations to the C++ bindings, and each catches
something the other two do not:

```bash
npx -y -p typescript tsc -p types/tsconfig.json     # the declarations, against types/typecheck.ts
npx -y -p typescript tsc -p examples/jsconfig.json  # the shipped .mjs, against the declarations
python3 types/check-surface.py                      # the declarations, against src/Js*.cpp
```

`tsc` proves the declarations are self-consistent; it cannot prove they match the
bindings, because the bindings are C++. `check-surface.py` is that half, and it is
a name check only.

## What is not covered here

- **The runtime.** How a script is loaded, when each phase runs, and what a
  profile is are properties of the host rather than of this surface.
- **Environment variables and `settings.json` keys.** They configure the DLL, and
  are reachable from JavaScript only through `settings` and `render`.
- **The C++ API.** Nothing in `src/` is callable from a script; `d3d8.dll` exports
  one symbol, `Direct3DCreate8`.

## The module

`import { actors, console } from "gk"` and `import gk from "gk"` reach the same
objects: the default export carries one property per namespace, so
`gk.actors === actors`.

A C module's named exports are values fixed at instantiation. The namespaces are
therefore **objects**, and the live state is on their properties, which is why
there is one `"gk"` module instead of one module per namespace.

`menus` is not an export. It is only ever the argument to `setup_menus`.

There is no global `console`. The host installs none; `log`, `info`, `warn`,
`error` and `debug` are on the `console` this module exports.

## Entry-module contracts

A profile's entry module (`core.script`, `main.mjs` by default) may export two
functions. Neither is required; a module exporting neither still loads.

| Export | Type | Called |
|--------|------|--------|
| `setup_menus` | [`SetupMenus`](/api/js/types/gk.gk.SetupMenus.html) | Once at startup, after the game has filled its own menus. Its argument is the only route to `Menus`. |
| `draw_gui` | [`DrawGui`](/api/js/types/gk.gk.DrawGui.html) | Every frame the F11 overlay is open, inside an active ImGui frame. Its argument is the only route to `ImGui`. Throwing disables it for the rest of the session. |

A module loaded out of a mod also carries
[`import.meta.mod`](/api/js/interfaces/gk.ImportMeta.html), the `Mod` it belongs to.
It is `undefined` in a profile's own `main.mjs` or `boot.mjs`, which the
declaration cannot distinguish and therefore types as present.

A mod's script exports the same two names into slots of its own, called alongside
the profile's and disabled independently if either throws.

## Levels

A script-defined level is an ordinary module whose namespace is the description
`levels.add` takes.

| Symbol | What it is |
|--------|-----------|
| [`LevelMap`](/api/js/interfaces/gk.gk.LevelMap.html) | The `map` export: geometry, bitmap, camera plane, shadow object. Validated at registration. |
| [`LevelBody`](/api/js/interfaces/gk.gk.LevelBody.html) | The hooks: `includes`, `define`, `populate`, `setup`, `message_received`. |
| [`LevelModule`](/api/js/interfaces/gk.gk.LevelModule.html) | Both of the above, as a module namespace. |
| [`LevelDescription`](/api/js/interfaces/gk.gk.LevelDescription.html) | Both of the above, as one inline object. |
| [`Level`](/api/js/interfaces/gk.gk.Level.html) | The handle each hook receives. |

## ImGui

[`ImGui`](/api/js/interfaces/imgui.ImGui.html) is a type, not a module. There is
no `"ImGui"` import and no global: an ImGui call outside `draw_gui` is not inside
a frame and does not work, so that callback's argument is the only reference to
the object.

`types/imgui.d.ts` is **generated** from `imgui-quickjs/imgui-quickjs.cpp` by
`python3 types/gen-imgui-dts.py`, which infers each parameter's type from the
`JS_To*` call the C++ wrapper makes and prints an `any` count that must stay 0. It
is not hand-edited.

Widgets return their new state instead of writing through a pointer, and optional
trailing arguments are an options object, not positional:

```js
const r = ImGui.SliderFloat("camera distance", camera.distance, 100, 3000);
if (r.changed) camera.distance = r.value;
```

## Conventions the whole surface follows

- **Every lookup mints a fresh wrapper.** `actors[1] !== actors[1]`. Compare
  `.id`, never object identity. A `MenuItem` is the one exception: `add_item`
  returns the same object its callback receives.
- **A wrapper can go stale.** An `Actor` or `Role` holds a raw game pointer that
  the engine frees without notice. `.valid` is the check; any other access on a
  destroyed one throws.
- **A collection lookup can miss.** `actors[12]` is `Actor | undefined`.
- **An actor is always the object.** No member anywhere takes an id or a token
  name.
- **`actor.kind` is a discriminated union.** `if (a.kind === "turret")` narrows to
  `TurretActor`, which is how a subclass-only member is reached.
- **Failure throws.** A boolean return answers a question: `actor.damage()` is
  "did it land", rather than reporting success.
- **A position is `{x, y, z}`.** An array is rejected.
- **`tokens` is the only writable collection**, and writing is an upsert.
- **Not every mutator replicates.** Some engine setters broadcast and some do not;
  `ActorBase`'s documentation lists which is which. The difference is invisible in
  single player and a silent desync otherwise.
- **Every `render` setting persists and nothing on `render.debug` does.**

## Design records

The reasoning behind this surface is not in the generated pages. It is in the
repository's own notes: `js_bindings_notes.md` for the binding layer,
`script_host_notes.md` for the host and the REPL, `make_role_notes.md` for `make`
and `gls`, `custom_levels_notes.md` for `levels`, `mod_loading_notes.md` for
`mods`, `profiler_notes.md` for `prof`, and `vulkan_renderer_notes.md` for
`render`.

Three of those arguments are written up on this site:

- [Why the script host boots twice](/explanation/why-the-script-host-boots-twice/): why
  there are two entry modules, and why `menus` and `ImGui` are callback arguments rather
  than exports.
- [Why mods are named, never discovered](/explanation/why-mods-are-named-never-discovered/): the
  reason `mods.load` and `mods.enable` are two calls and neither scans anything.
- [One settings file, many owners](/explanation/one-settings-file-many-owners/): why
  `settings` hands out a live tree instead of a parsed copy, and why nobody calls `save()`.
